# Drift performance audit, 2026-11-21

Tracking issue: #115. Start at [README.md](README.md) for the short version.

Numbers below are measured on main at `c16dc11` unless a line says `afc376f` (the first run, six commits
earlier). Those commits rewrote parts of the street view, so street numbers from `afc376f` are history only.

## 1. Summary

The game holds 60 fps at rest on both GPUs. The lag comes from these causes, biggest first:

1. **Debug builds in the street view.** p50 is 17.9 ms and 910 of 1200 frames miss 16.6 ms. `trees_draw` alone
   takes 12.1 ms per frame in debug and 0.97 ms in profile (#101).
2. **Route planning blocks the frame loop.** Frames up to 44 ms (#86, #100).
3. **Route lines are the largest CPU cost.** 2.5 to 4.2 ms per frame against a 4 ms budget (#96).
4. **The game starts on the integrated GPU.** 5.6 ms against 1.5 ms per frame (#89, #94).
5. **Other cars have no culling.** 8.4 ms at 256 cars (#102).
6. **No vsync.** 60 fps on a 165 Hz panel: likely tearing and uneven frames, not captured on the display
   (#90, #99).

Also found: a heap corruption on exit after the street view (#92), the bench is red on main because of
`ship_step` (#95), and the first frame takes 623 ms against a 100 ms budget (#87, #105).

## 2. Method and limits

**Machine:** AMD Ryzen 9 7940HS (8 cores, 16 threads), 16 GB DDR5-6400, Radeon 780M + GeForce RTX 4060 Laptop,
Windows 11 26300, on AC power, Balanced plan, panel 2560 x 1600 at 165 Hz, external 1920 x 1080 at 59 Hz.
**Compiler:** `dev-2026-11-nightly:9a69916`, not confirmed to be the pinned `dev-2026-11a` (#88).

**Build and run:** profile build (`-o:speed -debug -define:DRIFT_PROFILE=true`), script mode, window 1440 x 900, no
vsync and no fps cap unless a row says so. The first 150 frames are warm-up, then 600 to 1200 frames are measured.
Frame times are real time from one `game_update` to the next.

**Instrumentation (local, not in this repo):** about 90 spall zones, GL call counters and GL timestamp queries per
pass. The counters needed a small C shim, which the Odin-only rule keeps out of the repo. #93 brings
the zones in properly.

**Not measured:**
- Cache and branch misses: `perf`, cachegrind and heaptrack are not available on this Windows machine.
- The network path live: script mode disables weather fetch, peer node and presence. Those findings come from code.
  The 256 other cars are simulated.
- What the display shows: tearing and pacing on the panel are derived from the refresh rate.
- Noise: each scenario ran once per configuration, the bench three times. Treat differences under ~0.3 ms as noise.
- Cap, vsync, release and music runs exist only for `afc376f`.

## 4. Largest costs

### CPU
- `draw_path_strip`: 2.48 ms in navigation, 4.24 ms on the plan screen with routes (#96).
- `others_draw`: 8.4 ms at 256 cars (#102).
- `collide_car`: 23 to 30 calls and 0.92 to 1.35 ms per street frame, 5.4 ms in debug (#103).
- `trees_draw`: 0.8 to 1.0 ms, 12.1 ms in debug (#101).
- `layers_draw_ground`: 0.27 to 0.51 ms (#98).

### Spikes
- Planning routes: up to 44 ms, one `route` up to 33 ms, 205 ms in debug on `afc376f` (#100).
- Scan animation: up to 7.0 ms, 10.6 ms on `afc376f` (#97).
- Tile builds in street_low: houses 1.2 ms and trees 2.6 ms peak in profile, tree tiles up to 17.5 ms in debug (#111).
- Music: 2.8 ms every 93 ms while on, `afc376f` (#112).

### GPU (780M, mean ms per pass; all passes in `data/gpu-passes-*.csv`)
- Map view: road lines 2.9 to 3.1, buildings and trees 0.9 to 1.0, globe 0.4 to 0.5, areas 0.3.
- Street view: houses 1.3 to 1.4, land and areas 0.5 to 0.7, shadows 0.6, sky 0.3, trees 0.2.

**Arenas:** perm 20.2 MB after init (13.9 MB on `afc376f`), plus lazy street data. Frame arena 28 to 52 KB at rest, 1.4 MB in
navigation, 8.5 MB peak in the street view, 65 MB on frame 0. Route 8.6 KB of 1 MB. Plan 25 KB of 1 MB, but it
grows with reroutes (#104). The frame arena reset costs at most 0.31 ms on average in the street view.

**Active against capacity (last frame):** house tiles 54 / 192 and road tiles 21 / 192 on `c16dc11` (182 and 63 on
`afc376f`, before the view shrank to 1.6 km), town tiles 87 / 192, nature tiles 90 / 192 (`afc376f`), labels 273 / 1024, wind particles 900 / 900, A* nodes 13392 / 203346, map segments 225885, all
drawn.

**Layout:** the structs have little padding and hot data is already flat. `Tile` is the one clear hot/cold case: 136 B,
the slot search reads only the 8 B key (#111).

**Estimate against measurement (rules.txt):** `road_nearest_edge` takes 407 us over 151305 points, 2.7 ns or ~11 cycles
per point, which fits one divide and two square roots. The algorithm is the issue, not the code. `height_at` takes 42-52 ns
against 10-18 ns warm, which fits random access to a 2.2 MB grid on a 1 MB L2; that cache explanation is inferred.

## 6. IO and threads (from reading the code)

- Network runs on its own threads; each connect, send and receive has a timeout.
- No total deadline, no DNS timeout, so `node_stop` can hang (#106).
- Small file writes, synchronous logging and ed25519 signing run on the frame thread (#108).

### Parallelization candidates

| Candidate | Allowed | Needs first | Verdict |
|---|---|---|---|
| Asset inflate at startup | Yes | Inflate buildings once | #105 |
| Music synthesis | Yes | Chunk ring buffer | #112 |
| Tile mesh building | Yes | Arena per worker, `collide_build` first, upload on main | #111 |
| Route start / poll | Owner decides | Own grid and arena, copied inputs, fixed tick handover | #86 |
| Terrain, weather, ship, nav | No | Rule: no threads in simulation | Not doing |
| SIMD in wind and height sampling | Yes | - | Not doing: all wind work is 0.2 ms |

### Open questions for nasr

- #86 may route planning run on a worker thread with a start / poll API?
- #87 does the 100 ms startup budget include creating the window?
- #88 is dev-2026-11-nightly:9a69916 the pinned Odin dev-2026-11a?
- #89 should the game ask Windows for the discrete GPU by default?
- #90 should the game turn vsync on instead of the fixed 60 fps cap?
- #91 do we keep the unused live partner code (trip_start and its chain)?

### Deliberately not doing

- Broad SoA or SIMD rewrites: the loops involved cost under 0.3 ms together.
- Struct padding work: a few bytes, not measurable.
- Another arena strategy: resets are cheap.
- Turning MSAA or shadows off by default: a picture quality decision (#113).
- Threads in simulation code without the owner's answer.
